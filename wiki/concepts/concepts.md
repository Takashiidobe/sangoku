# Unicode lookup tables

_created 2026-11-06_

## Target rule

Avoid Unicode-property and Unicode-case APIs in LR35902 code unless their lookup
tables and ROM cost have been deliberately accepted. These APIs can pull fixed
Unicode lookup data into the program even when the runtime input happens to be
ASCII. Use an ASCII-specific API when ASCII behavior is the intended behavior.

Do not use runtime panics or target-only stubs to imitate these APIs. They have
stable Unicode behavior on other Rust targets, and callers may pass any valid
Unicode scalar value.

## APIs that use Unicode tables

- `char::is_alphabetic`, `is_alphanumeric`, `is_lowercase`, `is_uppercase`,
  `is_numeric`, and `is_whitespace`.
- `char::to_lowercase`, `to_uppercase`, and `to_titlecase`; `str::to_lowercase`,
  `to_uppercase`, `word_to_titlecase`, and `to_casefold_unnormalized` also use
  mapping data. String lowercasing additionally checks context for Greek final
  sigma.
- `str::trim`, `trim_start`, `trim_end`, and `split_whitespace`, which use
  Unicode whitespace rules.
- `Debug` formatting of `char` or `str` (`{:?}`), which checks Unicode
  properties to decide which characters to escape. This includes debug output
  generated by assertions.
- Unstable character-property APIs such as `char::is_cased`, `case`,
  `is_titlecase`, `is_xid_start`, `is_xid_continue`, `is_assigned`,
  `is_default_ignorable`, `is_case_ignorable`, and case-folding APIs.

The Unicode-aware APIs can reference lookup data even if a particular call uses
an ASCII character. Use `is_ascii_alphabetic`, `is_ascii_whitespace`,
`to_ascii_lowercase`, `split_ascii_whitespace`, or `trim_ascii` when their
ASCII-only semantics fit.

## APIs that do not use Unicode tables

UTF-8 operations such as `str::bytes`, `chars`, `char_indices`, reverse
iteration, `len`, and `is_char_boundary` decode or inspect UTF-8 without Unicode
property lookups. Their use alone should not require the property or
case-conversion tables.

## Why this matters

The tables are fixed read-only data, not a per-string allocation. A table is
needed only if its lookup path is present in the linked program. Legalizing
`u64` operations does not remove this data. The LR35902 backend has incomplete
wide-operation and static-data support, so avoid APIs above until those paths
are supported and their ROM cost is measured.

## Rust string behavior

The Rust fork uses upstream UTF-8 decoding and full Unicode tables for `str` and
`char`, including reverse iteration and escaping. `tests/core_rom/utf8.rs`
executes forward and reverse iteration at each UTF-8 width boundary on the
target, and `tests/core_rom/unicode_properties.rs` checks alphabetic,
whitespace and numeric properties.

## Measured cost

A 2026-11-07 opt-level z probe using the property and case APIs retained about
47 KB of Unicode code and data. The lookup code (two `bitset_search` and two
`skip_search` instantiations, case-conversion lookup, `u64::rotate_left`) is
about 42 KB; the tables are about 11 KB. Separate lowercase and uppercase ROM fixtures now link at opt-level z and
execute upstream results for Ä, ß, ǅ, and emoji (`sangoku-6o2`). The combined
fixture initially measured 32,864 bytes on 2026-11-09. Whole-byte shift lowering
reduced it to 32,715 bytes, leaving 53 bytes of section capacity. Plain UTF-8
`str` character counting and prefix/suffix
checks also link and execute. Larger Unicode programs can still require banking
or reduced retained code.

## Case conversion size breakdown

The 2026-11-09 baseline opt-level z maps count retained section bytes, including fixture
code and runtime, rather than the padded cartridge file size:

| Fixture | Total bytes | Data bytes | Code and runtime bytes |
| --- | ---: | ---: | ---: |
| Lowercase | 24,776 | 1,317 | 23,459 |
| Uppercase | 26,463 | 2,217 | 24,246 |
| Both directions | 32,864 | 3,413 | 29,451 |

Data includes fixture constants as well as Unicode tables. The conversion tables
already store ranges with signed deltas, parity for alternating case pairs,
16-bit code points within each plane, and separate expansion/exception tables.
Compressing all data to zero would save at most 3,413 bytes in the combined ROM.

The shared lookup alone emits 3,882 bytes and reserves 213 stack bytes. Its
`c >> 16` becomes sixteen rounds of `srl`/`rr` across four byte registers.
Selecting the upper two bytes directly should remove those shifts. Lowercase
and uppercase entry points cost 2,546 and 3,333 bytes; `CaseMappingIter::new`
costs 1,887 bytes and reserves 132 stack bytes. The combined fixture entry point
also costs 5,437 bytes, and expected-string UTF-8 decoding costs 1,870 bytes.
These totals measure more than an isolated table lookup.

Prioritize backend improvements to constant wide shifts, comparisons and
stack traffic before changing the table representation. These preserve upstream
Rust semantics and benefit unrelated code. Inspect missed inlining and retained
array/iterator adapters next; measure both code size and stack usage.

Further table compression could pack range fields or delta-encode sorted keys,
but requires decoding code and changes to the Unicode generator. Startup
decompression also consumes scarce WRAM. Measure the combined decoder and data
cost before adopting either scheme.

Whole-byte `u32` logical right shifts now lower to byte moves and zero fills.
`tests/core_rom/unicode_plane.rs` reproduces the lookup's plane/low-half split
with volatile input: its entry point shrank from 208 to 76 bytes. Lookup shrank
from 3,882 to 3,733 bytes, with its 213-byte frame unchanged. Lowercase and
uppercase fixtures shrank to 24,627 and 26,314 bytes. Other constant shift counts
retain their existing lowering; further stack/copy improvements remain open.

For fixed game text, convert case in host asset processing. For dynamic text,
use ASCII conversion or an explicit game-specific alphabet when appropriate.
Keep upstream `core` Unicode behavior intact: UTF-8 storage and iteration do not
require retaining every case-conversion table. Full dynamic Unicode casing
remains available when its measured ROM cost fits the game.

Minimal opt-level z probes reading dynamic input through `read_volatile` and
returning the low byte give a cleaner comparison than the multi-case fixtures:

| Operation | Retained section bytes | Entry point bytes |
| --- | ---: | ---: |
| `u8::to_ascii_uppercase` | 170 | 78 |
| `char::to_ascii_uppercase` | 544 | 452 |
| `char::to_uppercase().next().unwrap_or('\0')` | 17,483 | 602 |

ASCII probes retain no tables or other functions. Unicode retains 2,106 data
bytes, including its 24-byte table descriptor, and 15,377 code/runtime bytes.
The larger multi-case fixture additionally pays for iteration and comparisons
against expected UTF-8 strings. Even taking only the first uppercase character
retains the complete conversion: a general `char` may expand into three outputs.
`lookup` also retains generic binary searches and the array `map` machinery
(`try_map`, `try_from_fn`, and drain helpers) used to reconstruct those outputs.
These abstractions remain as emitted calls in the current toolchain.

The probes are under `build/case-probes/`. Constant `black_box` inputs still
allowed constant-specific simplification in these probes; use volatile inputs
for size comparisons that must retain dynamic behavior.

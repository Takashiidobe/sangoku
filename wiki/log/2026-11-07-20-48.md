# Fix volatile accesses and force MIR inlining (sangoku-30k.9.1.9.4)

_2026-11-07 20:48:53_

## Context

`sangoku-30k.9.1.9.4` (bug, P0): `sangoku run examples/hello.rs --opt-level 2`
printed `H` and spun forever (returning 129, 0x81); primes and sort failed the
same way, heap was fine. The size baseline had shown opt 2 was far smaller, so
fixing it also unblocked `sangoku-30k.9.1.9.5` (MIR inlining at s/z).

## Case

The serial write loop in `examples/hello.rs`:

```rust
write_volatile(SERIAL_DATA, byte);
write_volatile(SERIAL_CONTROL, 0x81);
while read_volatile(SERIAL_CONTROL) & 0x80 != 0 {}
```

## Cause

cg_clif lowered `volatile_load`/`volatile_store` as plain memory ops (a comment
claimed "Cranelift treats loads as volatile by default"). Once `read_volatile`
was MIR-inlined, Cranelift alias analysis forwarded the 0x81 store to 0xFF02
into the poll loop, so it never saw the hardware clear bit 7. Not caused by the
spill change: reverting wasmtime to before 940841a still failed.

## Fix

In `src/intrinsics/mod.rs` of cg_clif, scalar volatile loads and stores now use
`MemFlagsData::new().with_volatile(true)`; non-scalar loads keep the by-ref
path. Regression `tests/core_rom/volatile_poll.rs`, linked at opt 2 in
`core_link`. hello/primes/sort are correct at opt 2. Closed `.9.1.9.4`.

Then `sangoku-30k.9.1.9.5`: rustc only MIR-inlines at opt 2/3 by default and
Cranelift never inlines, so `rustc_command` passes `-Zinline-mir=yes` everywhere
(core/alloc builds too). At opt 0 Cranelift does no cleanup and
wide-overflow-mul's `gbc_main` reached 17450 bytes (> 16 KiB bank), so opt 0
adds `-Zinline-mir-hint-threshold=50`. Opt z, linked bytes:

```text
hello 6866 -> 2265     primes 22894 -> 9556
sort  18316 -> 8777    heap   63682 -> 32031
```

Opt 1/2/3/s match z; table in `wiki/concepts/size-baseline.md`. Tests: core sort
`sort_unstable` now links at z (moved to `tests/core_rom/sort_unstable.rs`); the
formatting/capacity diagnostics test uses `programs/oversized_formatting.rs`.
nextest 160/169 expected; the 9 failures are `sangoku-vmq`.

## Alternatives

Threshold 50 at z was worse for every example. Filed `30k.9.1.9.8`: opt-0
policy/default level (`sort_unstable` needs 57 KB at opt 0).

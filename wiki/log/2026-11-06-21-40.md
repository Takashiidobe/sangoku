# Allow 16-bit addresses in CLIF and enable the verifier (sangoku-7qz.6)

_2026-11-06 21:40_

## Context

The Game Boy has 16-bit pointers, but Cranelift's meta definition of the `iAddr`
type variable was `ints(32..64)`, so a hand-written `load`/`store` with an `i16`
address failed the CLIF verifier. The release backend only worked because
`cg_clif` ran with `enable_verifier` off, which also left the regalloc checker
off. sangoku-7qz.6 (P0) asked how to type 16-bit pointers and to verify `i32`
load/store; widening `iAddr` was the preferred answer so the verifier can stay
on.

## Case

`load`, `store`, `func_addr`, `stack_addr` and `call_indirect` with `i16`
addresses. The latter three could not even be written in textual CLIF at `i16`
(the type set rejected it).

## Before

Verifier rejected `i16` addresses; `enable_verifier` was off for release
`cg_clif`.

## After

`func_addr`, `stack_addr` and `call_indirect` became expressible and lower. The
matrix has nothing rejected by the verifier any more. Blank ROM and all fixtures
pass with the verifier on.

## How

`cranelift` meta `shared/instructions.rs` now defines both `iAddr` type
variables as `ints(16..64)`. `cg_clif`'s `enable_verifier()` returns true for
`z80`, which also turns on the regalloc checker. `tools/coverage_matrix.py`
probes `br_table` at `i32` because the verifier requires an `i32` index.

## Alternatives

Other targets still fail the separate "invalid pointer width" check for 16-bit
values. Remaining memory gaps (offsets beyond -128..127, `uload`/`sload`/
`istore`) became a new ticket (sangoku-7qz.21).

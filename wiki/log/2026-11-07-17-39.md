# Always use immediate-abort target panics (sangoku-30k.9.1.15)

_2026-11-07 17:39:35_

## Context

`sangoku-30k.9.1.15` (P1): examples using `core::fmt` did not fit a 32 KiB
cartridge (`rgblink` could not place `core::fmt::write` in ROM0). The map
analysis showed `sort` at 202267 bytes, mostly panic-message formatting
(`Formatter::pad_integral`, `fmt::write`), which a ROM cannot afford. The
immediate-abort experiment (`sangoku-afd`) makes panics trap instead of
formatting a message. Result: `sort` shrinks from 202267 to 115100 bytes at
opt-level 0; opt-level `z` is 116293 bytes. Both still exceed 32 KiB.

## Case

A slice out-of-bounds index in a ROM, e.g. `sort_unstable` on a byte array.

## Currently emits

`-Cpanic=abort` still builds the panic message through `core::fmt` and calls a
panic handler, retaining the formatting code.

## Should emit

A trap with no formatting. Real output: an out-of-bounds ROM now halts at the
trap vector without a panic handler. The gap: formatting still arrives through
`sort_unstable` -> heapsort -> slice range `index_mut` ->
`slice_index_fail::do_panic::runtime` -> `Argument::new_display<usize>` ->
`usize` Display -> `Formatter::pad_integral`. These helpers build the `usize`
`Display` arguments before the immediate-abort `panic_fmt` is reached.

## How

The LR35902 target default (`targets/lr35902.json` `panic-strategy`) and all
active rustc invocations (`src/main.rs`, tests, `tools/core_report.py`,
`tools/rust_fork.sh`) now use `-Cpanic=immediate-abort`. `core` and
`compiler_builtins` rebuild into `build/core/immediate-abort/opt-N` so old abort
libraries cannot be reused. The existing `cg_clif` `abort_immediate` lowering
emits a trap; no vendored changes were needed. New regression
`tests/core_rom/immediate_abort.rs` (run from `tests/core_link.rs`) halts at the
trap vector. Hello and primes pass. Full nextest 131/132 pass; only the `sort`
capacity failure remains. Clippy, fmt, LSP diagnostics and the hello ROM smoke
build pass.

## Alternatives

Not done: shrinking `sort` below 32 KiB; follow-ups remain on
`sangoku-30k.9.1.15` and `sangoku-xn2`, needing optimization without changing
upstream `core` semantics.

# Halting panic handler (sangoku-30k.9.1.7)

_2026-11-07 15:40_

## Context

`-Cpanic=abort` only removes unwinding; `core` still calls the panic handler
symbol `rust_begin_unwind` from its panic machinery, and the runtime defined no
handler. `sangoku-30k.9.1.7` (P1) asked to decide the behavior (halt loop,
optional message to a debug port) and provide it. Acceptance: a panicking
fixture links and halts under the emulator.

## Case

Any `core` panic path (bounds check, `unwrap`) in a ROM linked against `core`.

## Before

Undefined symbol `rust_begin_unwind`.

## After

`runtime/panic.asm` defines it:

```asm
rust_begin_unwind::
    di
.halt:
    halt
    nop
    jr .halt
```

It never returns and ignores its `PanicInfo` argument, so no formatting is
pulled into the ROM.

## How

`src/main.rs` and the lowered test harness link it when the assembly references
`rust_begin_unwind` without defining it, so a user `#[panic_handler]` still
wins. The test emulator gained `DI` (no-op) and `HALT` (pc stays).
`tests/panic.rs` enters the handler with a return address on the stack and
checks that it never returns, reaches the loop and leaves the stack alone. Not
pushed.

## Alternatives

Not done: an end-to-end panicking Rust fixture, because linking `core` waits on
`sangoku-30k.9.1.8` (per-function sections); optional debug-port message output
is left out.

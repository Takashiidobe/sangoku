# Fix i32 load/store register allocation crash (sangoku-7qz.16)

_2026-11-06 21:00_

## Context

The coverage matrix (sangoku-7qz.1) showed `load.i32` and `store.i32` with an
`i16` address panicking in regalloc at `machinst/compile.rs:77` ("register
allocation: SSA(VReg...)"). Every `u32`/`i32`/`f32` memory access in `core` goes
through these arms, so sangoku-7qz.16 (P0) had to land before anything else
could read 32-bit values from memory.

## Case

```text
function %ld(i16) -> i32 { block0(v0: i16): v1 = load.i32 v0; return v1 }
function %st(i16)        { block0(v0: i16): v1 = iconst.i32 0x12345678
                           store v1, v0; return }
```

## Cause

The `i32` arms of `Opcode::Load`/`Store` in the cranelift `lr35902` `lower.rs`
emitted four `LoadMem8`/`StoreMem8` instructions that shared one
`scratch_h`/`scratch_l`/accumulator vreg trio. Those operands are early defs, so
the second instruction redefined a vreg: not SSA.

## Fix

Each byte now gets fresh temporaries. Regression coverage:
`tests/fixtures/lower/load-store-i32.clif` (FileCheck on the emitted assembly)
and `tests/lowered.rs`, which lowers
`tests/fixtures/emulate/load-store-i32.clif`, assembles it with
`rgbasm`/`rgblink` and runs it in the emulator: load returns the four bytes in
`A`,`B`,`C`,`D`; store of `0x12345678` writes `78 56 34 12` and nothing beyond.
Matrix regenerated: no backend crashes remain.

## Alternatives

The emitted code is poor (`push`/`pop` around spill slots per byte, as the
fixture shows); that is register-pressure work, not part of this fix. LSP
(rust-analyzer) needs a few seconds to answer and returned nothing for the first
queries; use it with a short wait. Its diagnostics show old unused-import
warnings in `lr35902`.

# Core lowering report and driver (sangoku-30k.9.1.3)

_2026-11-07 14:17:48_

## Context

Non-generic `core` compiled to CLIF (3235 functions, 3221 lowering, 14 failing),
but generics only codegen when instantiated, so coverage needed a driver crate
instantiating a broad slice of core generics (iterators, slices, `str`, `fmt`,
`Option`/`Result`, `cell`, `mem`, `ptr`). Core rmeta that is metadata-only lacks
optimized MIR, so the driver cannot use it. `sangoku-30k.9.1.3` (P0) asked for a
command, a bounded nextest test that counts must not regress, and counts in the
README roadmap.

## Case

`tests/core_driver/driver.rs` compiled against `core` and `compiler_builtins`,
then every function lowered separately.

## Before

No way to see how much of `core` lowered, or why the rest failed.

## After

`tools/core_report.py` builds `core` and `compiler_builtins` through the backend
in CLIF-only mode, compiles the driver against them, lowers each function with
`sangoku-lower --probe` and groups failures by message:

```text
core              3235/3235 lower
compiler_builtins 1807/1807 lower
driver             771/771  lower   (opt-level 0)
```

Nextest `core_lowers_to_lr35902_without_failures` asserts zero failures and a
minimum driver size.

## How

Lowering passing moves the fallout to link time. Scanning the real asm for
undefined symbols found `__udivti3`, `__umodti3`, `__divti3`,
`__rust_u128_mulo`, `memcmp` and `rust_begin_unwind`. README roadmap updated.
Filed `sangoku-30k.9.1.5` to `.9.1.11` and closed `.9.1.4` as a duplicate.

## Alternatives

Deferred to a later optimization ticket, not a blocker: code size, which is core
3.2 MB and driver 507 KB at O0 against a 32 KiB bank. Not pushed.

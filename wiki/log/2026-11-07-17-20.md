# Core linking moves into the sangoku binary (sangoku-30k.9.1.14)

_2026-11-07 17:20_

## Context

Linking real `core` into a ROM (`sangoku-30k.9.1.8`) lived in the Python script
`tools/link_core.py`. `sangoku-30k.9.1.14` (P1) asked to move section pruning,
ROM0/ROMX placement and `core`/`compiler_builtins` asm caching into the
`sangoku` binary, always link `core`, build it once, and delete the script.

## Case

`sangoku build` of any program, with or without `core`.

## Before

Core-using programs needed a separate script; `sangoku build` used `needs_*`
checks in `main.rs` to choose runtime objects.

## After

`tools/link_core.py` is deleted and `sangoku build` does the work. First build
pays about 26 s for `core`; later builds of a `core`-using program take about
1.3 s. `no_core` programs need no special case: nothing from `core` survives
pruning if nothing references it.

## How

New `src/link.rs` holds the pure logic with unit tests: splitting assembly into
sections, reachability from `__rust_gbc_main` (any identifier another section
defines counts as a reference, local `.labels` ignored), parsing the `rgblink`
map for section sizes and free ROM0, placing sections into ROM0 then ROMX, and
choosing runtime objects (replacing the `needs_*` checks). `build_rom` now
always compiles `core` and `compiler_builtins` to assembly and metadata once per
opt level into `build/core/opt-N` (rebuilt when the backend library is newer),
compiles the program against that metadata so symbol hashes match, prunes,
probes sizes with an all-ROMX link, places, and links with `rgblink -t`.
`tests/core_link.rs` runs the real binary. Not pushed.

## Alternatives

Known leftover: cache staleness only tracks the backend library, not edits to
the `core` sources.
